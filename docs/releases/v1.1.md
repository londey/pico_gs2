pico_gs2 v1.1: the GPU on the ICEpi Zero v1.3, driven over its USB serial
port. v1.1 draws several times faster than v1.0 at the same interface
(`ID` reads interface version 2), so programs written for v1.0 run
unchanged.

## What it does

- Triangles, Gouraud shaded, depth tested against a 16-bit depth buffer,
  into a 640×360 RGB565 framebuffer, triple buffered and shown as 720p60
  over the board's HDMI port.
- Textures in SDRAM, RGB565 or ARGB4444, perspective correct, nearest or
  bilinear, repeated, clamped or mirrored; a colour combiner,
  (A − B) × C + D over the texture, the shade and two constants, as the
  N64's one-cycle mode; and an alpha test.
- Register writes over a 3 Mbaud serial link with credit flow control;
  GPU memory read and written over the same link (uploads, screenshots).
- A built-in scene (a spinning cube) while no host is connected.

## Performance (75 MHz)

| Scene | v1.0 | v1.1 |
|---|---|---|
| a clear | 9.1 ms | 0.05 ms |
| clear, then the screen covered by a bilinear 64×64 texture | 32.8 ms | 9.1 ms |
| the textured cube | 16.8 ms | 2.7 ms |
| a small (8×8 pixel) triangle in a strip | | about 260 cycles (3.5 µs) |

A 60 fps frame has room for about 6,500 fully drawn 8×8 blocks, 1.8
screens. The serial link, not the GPU, limits small-triangle scenes:
about 500 untextured triangles a frame in strips at 60 fps.
`host-interface.md` §15 has the full table and what follows for a host.

## Using gs-proto from a game

A cargo git dependency on this repository fails: cargo checks out every
submodule, and the board repository's nested ones have no URLs. Either
unpack `gs-proto-1.1.0.tar.gz` into the game's repository, or add this
repository as a submodule (`git submodule update --init` without
`--recursive` works) and depend on it by path:

```toml
gs-proto = { path = "pico_gs2/host/proto" }
```

## Not in v1.1

The SPI link from an RP2350 (designed, `host-interface.md` §11), alpha
blending, the second vertex colour (`ATTR1`) and meshes kept in SDRAM.
